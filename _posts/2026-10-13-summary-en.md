## [WiFi 7 Router Repurposed as 320 Msps SDR Receiver](https://github.com/h0m3us3r/w1700k-sdr) ⭐️ 8.0/10

Developer h0m3us3r has published an open-source project that replaces MediaTek's stock firmware on the Gemtek W1700K Wi-Fi 7 router's MT7996 radio with custom firmware reverse-engineered register by register, turning the router into a wideband software-defined radio receiver. The modified radio captures 14-bit IQ samples at up to 320 Msps across the 2.4, 5, and 6 GHz bands and streams them over 10 GbE via zero-copy UDP to a Linux host for live spectrum rendering. This project demonstrates that commodity Wi-Fi 7 hardware can deliver SDR capabilities previously requiring expensive dedicated equipment, potentially enabling budget-friendly spectrum monitoring, RF research, and signal analysis on widely available consumer devices. It also highlights how reverse-engineering closed radio firmware can unlock hidden capabilities in everyday networking gear. The radio streams raw 14-bit IQ samples without dropping any, and the project is not a full transceiver—it functions as a receiver only, with coverage limited to the 2.4/5/6 GHz bands rather than DC to daylight. Because the same MT7996 chipset is used, commenters believe the approach may also work on the Banana Pi R4, which has built-in PCIe for NVMe.

hackernews · djfergus · Oct 12, 12:41 · [Discussion](https://news.ycombinator.com/item?id=50055593)

**Background**: Software-defined radio (SDR) is a technique where radio signal processing is done in software rather than dedicated hardware, allowing one device to receive or transmit many different protocols and frequencies. Traditional SDR hardware like USRP or LimeSDR can cost hundreds to thousands of dollars, so hobbyists often look for cheaper alternatives. Wi-Fi 7 routers contain powerful RF front-ends and baseband chips designed for high-throughput wireless networking, and hackers have increasingly targeted these chips to repurpose them for general-purpose radio experimentation.

## [Codex CLI silently installs persistent self-updating daemon by default](https://github.com/openai/codex/issues/48195) ⭐️ 8.0/10

Since version 0.157.0, simply opening an interactive Codex CLI session silently starts a persistent background daemon (app-server --managed-daemon) that survives window closure, copies a ~374MB platform package into a versioned directory decoupled from the installed CLI, and launches a detached updater that checks for updates hourly. The behavior is undocumented and has no official setting to disable it, sparking a 480-point, 245-comment GitHub issue. Codex CLI is a widely used AI coding agent, so a silent always-on daemon changes the trust and resource model for every developer who runs it, affecting disk usage, permissions, and predictability of the tool. The backlash highlights growing scrutiny of how AI coding assistants install background services and auto-update without explicit user consent. The daemon copies roughly 374MB per version into a versioned directory and, according to one user, accumulated about 12GB of old versions; another reported that auto-updating randomly broke permissions and made .git read-only, blocking tasks. A feature flag exists in ~/.codex/config.toml ([features] daemon_auto_start = false), and the daemon writes pid and lock files under ~/.codex, but none of this is documented.

**Background**: Codex CLI is OpenAI's lightweight coding agent that runs locally in the terminal, typically installed via npm as @openai/codex. A background daemon is a long-running process that keeps running after the terminal closes, often used to manage sessions or perform updates. The controversy centers on whether such a persistent, self-updating component should be installed silently by default rather than being opt-in.

## [PS2 games statically recompiled to run in browsers via WebAssembly](https://github.com/snuri00/ps2-web-recomp) ⭐️ 8.0/10

Developer snuri00 published ps2-web-recomp on GitHub, a project that statically recompiles PlayStation 2 games into C++, compiles them to WebAssembly, and links them against a reimplementation of the PS2 OS and hardware that renders with WebGPU. The first title, Gran Turismo 4, reportedly runs at full speed (50 FPS) on a laptop's integrated GPU at twice the PS2's native resolution, all without a traditional emulator. This demonstrates that static recompilation can bring console games to the web with native-like performance, potentially opening a new distribution path for game preservation that bypasses traditional emulators. It also highlights a growing trend of recompilation projects across consoles, from N64 to PS Vita, and raises questions about performance, legality, and trust in community-built binaries. The project translates the PS2's Emotion Engine MIPS machine code ahead of time into C++, then compiles it to WebAssembly, and links it against a reimplementation of the PS2 OS and hardware that draws with WebGPU. It is the sibling of the same author's psp-web-recomp and follows the same method, but so far only the first title has been brought up.

hackernews · deadxwarrior · Oct 12, 06:46 · [Discussion](https://news.ycombinator.com/item?id=50052251)

**Background**: Static recompilation is a form of binary translation in which a program's machine code is translated from one instruction set architecture to another ahead of time, rather than at runtime as in dynamic recompilation or emulation. This approach can produce native-like performance because the translated code runs directly on the target platform, and it has been used in projects like N64Recomp to port Nintendo 64 games. The PS2's main CPU is the Emotion Engine, a MIPS-based processor that has historically been challenging to emulate efficiently, as seen in emulators like PCSX2.

## [Python 3.15 Released with PEP 810 Explicit Lazy Imports](https://simonwillison.net/2026/Oct/12/python-3-15/) ⭐️ 8.0/10

Python 3.15 has been released, with the What's New guide curated by release manager Hugo van Kemenade. The headline feature is PEP 810 explicit lazy imports, which let developers write `lazy import json` or `lazy from pathlib import Path` so the module is only loaded when its symbols are first used. The release also adds PEP 798 unpacking in comprehensions, and it marks the end of support for Python 3.10. Lazy imports directly address a long-standing pain point: importing heavy dependencies such as sentence_transformers can add multiple seconds to CLI startup, which is exactly why Simon Willison had to document manual lazy-import workarounds for his LLM plugin system. A first-class, explicit language feature makes this optimization safe and predictable for the entire Python ecosystem, while the retirement of 3.10 pushes library maintainers to adopt 3.11-era features. PEP 810 is the second attempt at lazy imports in CPython after the implicit-everywhere PEP 690 was rejected by the Steering Council in 2022-2023 over complexity and unpredictability; the new design is entirely explicit and opt-in. The feature first shipped in Python 3.15 beta 1 on 7 May 2026, and the new comprehension unpacking syntax `[*sublist for sublist in lists]` is equivalent to nested loops like `[x for L in lists for x in L]`.

rss · Simon Willison · Oct 12, 18:15

**Background**: Python is a widely used open-source programming language, and each annual release adds syntax and performance improvements while dropping the oldest supported version. A PEP (Python Enhancement Proposal) is the formal design document through which language changes are proposed and approved. Lazy imports mean a module is not executed at import time but only when one of its names is actually used, trading a small amount of indirection for faster startup. Python 3.11, released in October 2022, is the version Willison can now target since 3.10 is no longer supported.
